# Development workflow and handoff

Start each session here. Read the [current requirements](SRS.md), [technical plan](TRD.md), and [decision log](DECISIONS.md) before changing the optimizer. Check the Git diff and use the current implementation and tests to verify this handoff.

| Stage | Work | Check before proceeding |
|---|---|---|
| 1. Baseline command | Add `build.sh`, the Python `kopt` entry point, and the permitted kit code it uses. Read the machine and emit the input unchanged. | The documented command works from a clean checkout and from another directory. |
| 2. First passes | Implement local constant folding and copy propagation, then add liveness and dead pure code removal. | Verify a beneficial rewrite and a case where each pass must preserve the original behavior. |
| 3. Batch validation | Compare originals with optimized outputs under the official validator, then measure cycles with the simulator. | Check public workloads across supplied machines, repeated-run determinism, and runtime on a generated large program. |
| 4. Performance work | Add fusion, register reuse, or scheduling in separate changes. | Keep changes with measured benefits. Investigate slower cases and retain a reproducer for failures. |
| 5. Submission | Update the root README and the seven required design sections. Build from a clean checkout and record demo and benchmark evidence. | Review the submission checklist and confirm organizer access before sending the repository link. |

For each change, write down the fact that makes the rewrite safe. Add a small test when the public suite would miss the failure mode. Start with `const_chain`, `junk_dead`, and `common_subexpr` for wins, then run `dead_div_trap`, `sensor_sum`, and `alias_hazard` as guardrails. Include same-input cycle comparisons and record skipped validator inputs separately from passing inputs.

- **State (2026-11-12)** — Three new passes are implemented: proven polynomial summations, complete finite-domain specialization, and bounded scheduling. The replayable demo includes formulas, specialization, scheduling, and effects before traps. The repository contains all four required top-level files, executable entry points with LF line endings, and no copies of the organizer's benchmark or machine folders.

Against pre-change `16f0beb`, 262 pairs improved and 238 tied; none slowed. Default total: 23,918 → 16,690 cycles, against 103,671 original cycles. Other totals: few registers 32,407; no fused 19,115; slow memory 25,752; wide/fast 16,808. These summed sample totals are not the judging score. Default `sum_sq`: 13; `collatz`: 18; `spill_storm`: 19. Maximum observed optimizer wall time in the parallel matrix: under one second locally.
- **Fresh programs** — Stress seeds 60723 and 921730 passed 9,600 comparisons across four machines. `tests/summations.py` passed 64,480 comparisons across eight machines, including 2,080 bad-address traps. `tests/finite.py` passed 39,136 comparisons, including 168 division traps; it explicitly skipped 160 nonterminating references rather than counting them as matches. `tests/scheduling.py` passed 102,400 comparisons across eight machines, with 120 reordered pairs and checks of register reuse, memory, traps, and volatile blocks. These three targeted suites now run in Ubuntu CI.
- **Runtime and determinism** — A generated 100,001-instruction function completed in 1.14 seconds locally; a finite-domain budget-exhaustion case completed in 0.82 seconds and retained the ordinary optimizer output. Those two cases plus `sum_sq`, `collatz`, and `matmul4` produced identical bytes under hash seeds 1 and 87654321. These are local measurements, not judging-hardware guarantees.
- **Ubuntu release verification** — Revision `d50cd7e0e8d48a55d89493ef4a79c6dbd57bfc2b` passed on Ubuntu 22.04 x86-64 / Python 3.10.12 in 1 minute 33 seconds: build, 39 CLI tests, expanded demo, 500 sample pairs, 32,000 generated comparisons, 4,800 stress comparisons, and all 206,016 targeted comparisons. Subsequent changes in this release only clarify documentation and record this evidence.
- **Limits and next performance target** — Finite specialization can slow an individual input while improving the full proven domain's geometric mean; scheduling models short paths and skips spilling programs. Summation lowering requires a narrow loop shape and a bound through 255. Investigate spill-aware scheduling and memory/loop transformations using unseen generated kernels next. The other implementation's reported default total of 8,700 remains unverified and below ours; do not claim winning performance. See [Research](RESEARCH.md).
